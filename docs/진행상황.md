# 지금까지 진행상황 (팀원용 쉬운 설명)

> 한 줄 요약: **사진 → 무슨 음식인지 → 레시피 통계 → "나한테 위험한지"** 까지 코드로 연결됐고,
> 이제 **처음 보는 음식**을 잘 처리하기 위한 데이터 모으기와 학습(CLIP)을 시작한다.

---

## 1. 우리가 만드는 것
해외여행에서 처음 보는 음식을 찍으면, **내 알레르기 기준으로 위험한지**와 영양 정보를 알려주는 웹 앱 "찍먹".
음식 이름을 몰라도 된다.

```
① 내 알레르기 고르기 (예: 땅콩, 새우)
② 음식 사진 찍기
③ 결과: 🔴 새우 주의   ⚪ 땅콩 해당 없음   칼로리·나트륨
         [왜요?] "이 음식 레시피 대부분이 새우 육수를 써요..."
```

## 2. 바뀐 방향 (회의에서 정한 것)
| 전 | 지금 |
|---|---|
| MLOps(사용자 피드백으로 재학습) | **뺌.** 앱 목적은 "위험한지 판별"이라 정답 피드백이 꼭 필요하지 않음 |
| Streamlit | **웹 앱 (FastAPI 백엔드 + HTML 화면)** |
| 판정 방식 | **1단계 룰베이스 → 2단계 RAG** |

## 3. 전체 흐름
```
사진 ─> [학습 ① 분류 모델] 101종 중 무슨 음식? (후보 3개 + 확신도)
           │
     확신이 높다 ─ 예 ─> [1단계 룰베이스] 미리 만든 표에서 그 음식 줄을 찾음 ─┐
           │                                                            ▼
           아니오 (처음 보는 음식)                                 [판정] 내 알레르기 기준
           ▼                                                         🔴 주의 / 🟡 확인 필요 / ⚪ 해당 없음
     [2단계 RAG]                                                        ▲
       [학습 ② CLIP] 사진과 비슷한 레시피를 바로 찾음 ──> 같은 규칙으로 계산 ─┘
       + LLM이 이름 추정해서 교차 확인
           │
     [설명] LLM이 찾아온 표·레시피를 근거로 쉬운 말 설명
```

**꼭 기억할 원칙 3개**
1. **판정은 항상 같은 규칙(`knowledge/rules.py`)이 한다.** LLM은 판정하지 않는다 (이름 추정·설명만).
2. 1단계든 2단계든 결과는 같은 모양: **"알레르기 19항목 비율 + 레시피 수 + 출처"** → 판정 함수 하나로 처리.
3. **"안전하다"고 절대 말하지 않는다.** 레시피 30개 미만은 `정보 부족`, LLM 추정은 `추정` 표시.

## 4. 용어 정리
| 용어 | 쉬운 뜻 |
|---|---|
| **룰베이스** | 사람이 정한 규칙. 예: 재료에 `flour`, `noodle`이 있으면 "밀" |
| **알레르기 비율** | 그 음식 레시피 중 해당 재료가 들어간 비율. 라멘 레시피의 81%에 밀 → 밀 0.81 |
| **RAG** | 질문할 때 **우리 데이터에서 근거를 찾아 붙여서** LLM에게 주는 방식. 학습 아님. "자료 보고 답해" |
| **API** | LLM을 부르는 **통로**. RAG와는 별개 (API로 불러도 자료 안 붙이면 RAG 아님) |
| **파인튜닝** | 이미 학습된 모델을 우리 데이터로 **추가 학습** |
| **CLIP** | 사진과 글을 같은 공간에 놓아서 "이 사진 ↔ 이 글"이 얼마나 가까운지 재는 모델 |

## 5. 학습(딥러닝) 파트는 2개
| | ① 분류 모델 | ② CLIP 검색기 |
|---|---|---|
| 하는 일 | 사진 → 101종 중 무슨 음식인지 + 확신도 | 사진 → **비슷한 레시피를 바로 찾기** (처음 보는 음식용) |
| 어디에 쓰나 | 1단계 (아는 음식) + 1단계/2단계 나누기 | 2단계 RAG의 "찾기" |
| 모델 | ConvNeXt-Tiny 파인튜닝 (test top-1 0.89 / top-5 0.98) | CLIP 파인튜닝 (대조 학습) |
| 데이터 | Food-101 사진 10만 장 | 레시피 사진 + 레시피 제목·재료 짝 (노트북 03이 모음) |
| 담당 | 주한솔 | 박중현 |
| 덤으로 할 것 | 확신도 보정(temperature scaling), 처음 보는 음식 감지(energy 점수) | 학습 전 기본 CLIP, "비슷한 사진 찾기"와 먼저 비교 |

### 왜 CLIP이 필요한가? (자세한 근거·대안 비교·예상 질문: [`CLIP_왜쓰나.md`](CLIP_왜쓰나.md))
원래 2단계 계획은 **LLM이 사진 보고 이름 추정 → 그 이름으로 레시피 글자 검색**이었다.
문제: 연결 고리가 "LLM이 말한 이름 하나"라서, **이름이 틀리거나 레시피에 없는 표기면 끊긴다.**

CLIP은 **이름을 거치지 않고 사진 → 레시피로 바로** 간다. "이름 몰라도 된다"는 우리 앱 취지와 딱 맞고,
"RAG의 검색기를 우리 데이터로 학습시켰다"는 게 딥러닝 수업 발표 포인트가 된다.
LLM은 빠지는 게 아니라 **교차 확인(이름이 CLIP 결과와 맞나) + 설명** 역할로 바뀐다.

### CLIP으로 바로 가고, 비교는 그 안에서
다른 방법(분류 모델 175종으로 늘리기 = 목록 밖은 못 봄 / 비슷한 사진 찾기 = 사진끼리만 비교)보다
우리 목적("처음 보는 음식 → 레시피 글")에 CLIP이 가장 맞아서 바로 간다. 대신 숫자는 이렇게 남긴다:
- **학습 전 CLIP vs 파인튜닝 CLIP** → "우리 데이터로 학습시켰더니 이만큼 올랐다" (발표 핵심 숫자)
- **ConvNeXt vs CLIP** (Food-101 시험셋 정확도 + 서버 CPU 응답 시간) → 1단계를 누가 맡을지 결정

### ConvNeXt와 CLIP의 역할 차이
| | ConvNeXt | CLIP |
|---|---|---|
| 질문 | "101종 중에 **뭐야**?" | "이 사진이랑 **비슷한 레시피**는?" |
| 잘하는 것 | 아는 음식을 빠르고 정확하게 | 목록 밖 음식도 레시피에 연결 |
| 비유 | 메뉴 101개 외운 직원 | 요리책 100만 권 뒤지는 사서 |

둘 다 **판정은 안 한다.** 판정은 항상 룰(재료 규칙 → 비율 → 🔴🟡⚪).
레시피가 아예 없는 음식만 LLM이 **재료 목록을 추정**해 주고, 그것도 룰이 판정한다 (`추정` 표시).

## 6. 왜 이렇게 설계했나 (발표·보고용 당위성)

**문제 정의:** 한국인이 해외여행에서 처음 보는 음식을 만났을 때 — 메뉴 언어도, 음식 이름도, 알레르기 정보도 모른다.
타깃이 한국인이라 **한국 알레르기 표시 기준 19항목**을 쓴다 (평소 식품 포장에서 보던 그 기준).

| 설계 결정 | 이유 | 증거로 쓸 실험 |
|---|---|---|
| 사진에서 바로 판정하지 않고 **레시피 통계**로 | 육수·소스·반죽 속 재료는 사진에 안 보임. 같은 음식도 레시피가 달라서 "있다/없다"보다 **비율**이 정직함 | EDA 비율표 (음식별 레시피 차이) |
| 판정은 LLM이 아니라 **룰** | LLM은 지어낼 수 있음. 룰은 근거("재료에 shrimp")가 남고 법 기준과 1:1 | **정답지 20~30종: 룰 판정 vs LLM 직접 판정의 경고 놓침(FN) 비교** ← 가장 강한 증거 |
| **ConvNeXt → CLIP** 순서 | 아는 음식은 작은 모델이 빠르고 정확하게, 모를 때만 무거운 모델 ("싼 모델 먼저" 구조) | ConvNeXt vs CLIP 정확도 + 서버 CPU 응답 시간 |
| **CLIP 파인튜닝** | 기본 CLIP은 서양 웹 사진에 치우침 → 우리 레시피 사진·글로 음식 검색에 맞게 다듬음 | 처음 보는 음식(후보 일부를 빼둔 시험셋)에서 학습 전 vs 후 |
| **확신도로 1·2단계 나누기** | 모르는 음식을 아는 음식으로 착각하면 판정이 틀림 | 확신도 보정 전/후, 처음 보는 음식 감지 (AUROC, TPR95) |
| 애매하면 **가장 위험한 쪽으로** 합치기 | 알레르기 앱은 놓치는 것(FN)이 괜한 경고(FP)보다 훨씬 위험 | 1등만 vs 합치기의 FN·FP 비교 |
| 레시피 30개 미만은 **정보 부족** | 근거가 적을 때 "없다"고 말하지 않기 위해 | 표본을 줄여가며 비율이 흔들리는 정도 |
| LLM은 파인튜닝 대신 **RAG** | 학습 데이터 없음, 근거를 붙여야 지어내지 않음, 데이터가 바뀌어도 재학습 불필요 | 설명 문장의 숫자가 표와 일치하는지 샘플 검수 |
| **Food-101 + 레시피 100만 개** | 공개 벤치마크라 논문과 비교 가능, 레시피가 사진과 글을 이어 줌 | 모델 성능을 논문 수치와 비교 |

**발표 흐름:** 문제 → 핵심 아이디어(안 보이는 재료를 레시피 통계로, 판정은 법 기준 룰) → 딥러닝 2개(ConvNeXt·CLIP) → 안전장치 → 실험 숫자

**판정 기준 (임시값, 나중에 실험으로 다시 정함)**
- 레시피 비율 60% 이상 `주의` / 20% 이상 `확인 필요` / 그 아래 `해당 없음`
- 모델 1등 확신도 0.8 이상 → 1등 음식만 / 0.3 이상 → 상위 3개 중 **가장 위험한 쪽으로** 합침 / 그 아래 → 2단계

**02 노트북에서 알게 된 것**
- 레시피 거의 전부에 사진 주소가 있음. 표본 90개 중 **약 67%가 아직 열림** → 사진+레시피 짝 수만 개 확보 가능
- 한식(김치찌개, 떡볶이, 김밥 등)은 레시피가 30개 미만 → `정보 부족`. AI Hub 한국 음식 사진으로 보완 검토
