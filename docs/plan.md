## 유라 · MLOps (`streamlit_app/`, `trigger/`, `share_storage/`)
1. 앱 실행 확인 (best.pt 넣고 사진 → 후보 3개 → 정답 저장)
2. 관리자 화면: pending 사진 검토 → 승인/수정/제외 → data/ 로 이동
3. 재학습 코드 (노션 2장 규칙: 기존 Train 일부 + 과거 피드백 일부 + 새 피드백, Val/Test는 학습 금지)
4. 승격 기준(기존 음식 정확도 하락 1%p 이내 등) 통과 시 model/ 교체, version +1
5. 새 음식 승인 시 classes.txt 추가 + 룰베이스 담당에게 표 행 추가 요청
6. 학과 서버 배포

## 한솔 · 모델 (`modeling/`)
1. 학습 코드를 `modeling/`에 올리기
2. `modeling/model.py`의 `load_model`·`predict`를 한솔님 모델 구조에 맞추기 (함수 모양은 유지)
3. 최종 가중치 → 학과 서버 `food101/checkpoints/`, 앱용으로 `share_storage/model/best.pt`
4. 잊어버림 실험: 새 음식 추가 재학습 후 기존 101종 정확도가 얼마나 떨어지는지

## 중현 · 룰베이스·LLM (`knowledge/`, `llm/`)
1. **표 완성**: Colab에서 `knowledge/build_table.py` 실행 → food_table.csv에 영양 중앙값 칸 추가
2. **판정 기준 정하기** (`knowledge/lookup.py`)
   - 알레르기 '높음/가능' 기준 (지금 50% / 10%, EDA 때는 60% / 20%)
   - 나트륨 높음 기준 (하루 권고 2,000mg 대비 1인분 비율)
3. **LLM 연결** (`llm/explain.py`)
   - ① lookup 결과를 쉬운 말로 설명, 사용자 질문 답변 (판정은 바꾸지 않음)
   - ② 새 음식 등록 때 영어 별칭·검색어 제안 → 레시피 수 확인 → 사람 확인 → `class_map.csv`
   - ③ 표에 없는 음식은 "추정" 표시를 붙인 참고 정보만
   - 제공자: API(품질 좋음, 비용·키 필요) vs 학과 GPU 오픈소스(무료, GPU 공유 부담) — 팀 결정
4. **새 음식 레시피 찾는 순서**: 1M_Final → 다른 공개 데이터(식품안전나라 등) → LLM 추정(신뢰도 낮음 표시)
   - `notebooks/02_새음식후보_집계.ipynb`로 1M_Final에 레시피가 충분한 새 음식 후보 확인

## 서준영 · 데이터·평가 (`evaluation/`, 만들 예정)
1. 공용 데이터 분할 파일 (Food-101 train/val/test 고정) → MLOps 재학습에서도 같은 분할 사용
2. 사용자 사진 평가셋: 실제 촬영 사진 모음 (피드백 사진과 별도, 학습 금지)
3. 알레르기 정답지: 음식 20~30종을 실제 레시피로 사람이 확인 → 룰베이스 경고가 놓친 비율(FN) 측정
4. 발표용 EDA 그림 정리
